# 一行配置的 0 ↔ 37：SRAM 宏 LVS 根因的三态对照

> 设计：`sram_test`（sky130_sram_1kbyte_1rw1r_32x256_8 + 少量标准单元）
> 工具：OpenLane 1.x / netgen
> 结论：`FP_PDN_MACRO_HOOKS` 参数顺序写反，导致宏电源脚悬空；改一行，LVS 从 37 归零。

---

## 1. 三态对照（核心证据）

同一个设计、同一套工具、同一份 RTL，**只改 `config.json` 里的一行**：

| 状态 | run | `FP_PDN_MACRO_HOOKS` | `Total errors` |
|---|---|---|---|
| A（修好） | `run_1114_lvsfix` | `"u_sram VPWR VGND vccd1 vssd1"` | **0** |
| B（回退） | `repro_lvs` | `"u_sram VPWR VGND VPWR VGND"` | **37** |
| A'（再改回） | `repro_fix2` | `"u_sram VPWR VGND vccd1 vssd1"` | **0** |

B 与 10 月 24 日首次失败的 `openlane_test`（37 错）**报告逐字相同**——说明这一个变量就是全部原因。

---

## 2. 现象：37 不是 37 个 bug

```
LVS reports:
  net count difference = 2
  device count difference = 0
  unmatched nets = 4
  unmatched devices = 18
  unmatched pins = 13
  property failures = 0

Total errors = 37
```

**自洽校验**：`2 + 4 + 18 + 13 = 37`。`Total errors` 是**四类问题求和**，不是 37 个独立故障。

| 数字 | 值 | 含义 | 性质 |
|---|---|---|---|
| `net count difference` | 2 | 版图 204 网 vs 网表 202 网，多 2 个 | **根因** |
| `device count difference` | 0 | 器件数一致，**排除器件库问题** | — |
| `unmatched nets` | 4 | 版图侧 `u_sram/vccd1`、`u_sram/vssd1` + 网表侧 `_NC30`、`_NC31` | 根因体现 |
| `unmatched devices` | 18 | 9 对 fill/decap 因电源网错位被判不匹配 | 连锁 |
| `unmatched pins` | 13 | SRAM 实例引脚错位（`dout[1]` vs `din[0]` 一类） | 连锁 |

因果链：

```
net 多 2 个（一电一地）
  → 宏的 vccd1 / vssd1 在版图里是独立网，没接到 VPWR / VGND
  → 挂在 VPWR 上的 fill/decap 电源网错位（18 个器件）
  → 器件引脚编号整体错乱（13 个 pin）
  → 合计 37
```

**一个根因，36 个连锁。**

## 3. 取证：物理证据

```bash
grep -n "vccd1\|_NC30\|vssd1\|_NC31" \
  designs/sram_test/runs/repro_lvs/logs/signoff/40-sram_test.lef.lvs.log
```

```
[833] Net: u_sram/vccd1 | Net: _NC30
[836] Net: u_sram/vssd1 | Net: _NC31
```

左侧是**版图侧**（`u_sram/vccd1` 成了独立网），右侧是**网表侧**（`_NC30` = 未连接节点）。
修复后这两行消失。

旁证：同日志 fill/decap 对比段 `VPWR = 173 | 174`、`VGND = 173 | 174`（电源网编号错位 1）。

---

## 4. 根因：参数顺序填反，且工具不报错

`FP_PDN_MACRO_HOOKS` 的字段顺序是：

```
<实例名> <电源网> <地网> <电源引脚> <地引脚>
```

原来写成 `"u_sram VPWR VGND VPWR VGND"`——第 4、5 位（**引脚名**）填成了网名。

OpenROAD 内部执行 `add_global_connection -pin_pattern VPWR -inst_pattern u_sram`：

- 宏的真实电源脚叫 `vccd1` / `vssd1`（LEF 里定义了），不叫 `VPWR` / `VGND`
- `-pin_pattern VPWR` 在 `u_sram` 上**匹配 0 个 iterm**
- **OpenROAD 对这种"匹配不到"不做任何报错**，静默跳过

于是 PDN 阶段没给宏电源脚连任何东西，版图侧 `u_sram/vccd1` / `u_sram/vssd1` 成了两个浮空网。

**黑盒 `.v` 不需要写电源脚**：`write_powered_verilog` 会按 LEF 的 `USE POWER` / `USE GROUND` 自动补。
证据在 `tmp/signoff/37-sram_test.pnl.v` 的 `u_sram` 实例：

```verilog
u_sram ... ( .vccd1(VPWR), .vssd1(VGND), ... );
```

## 5. 一个被实测否掉的猜测

最初怀疑 `sram_blackbox.v` 里 `wmask0 [31:0]`（LEF 只有 `wmask0[0..3]` 四位）也贡献了那 13 个未匹配引脚。

**实测否掉**：`repro_lvs` 中 `wmask0` 已是 4 位，`unmatched pins` **仍是 13**。

结论：13 个 pin 完全是电源悬空的连锁，与 `wmask0` 位宽无关。
（`wmask0` 32→4 是一个独立的接口 bug，该修，但它不是 LVS 错因。）

## 6. 为什么流程还打印 `[SUCCESS]`

`config.json` 里三个开关：

```json
"MAGIC_DRC_USE_GDS": false,
"QUIT_ON_LVS_ERROR":  false,
"QUIT_ON_MAGIC_DRC":  false,
```

`QUIT_ON_LVS_ERROR: false` 的含义是：**LVS 照跑，失败不中断流程，继续往下做 DRC。**

所以：

| 层 | 判据 | 不能看什么 |
|---|---|---|
| STEP 40 是否执行 | `logs/signoff/40-*.lvs.log` 存在 | — |
| **LVS 结果** | `reports/signoff/40-*.lvs.rpt` 的 `Total errors` | ❌ 不能看 `[SUCCESS]` |
| 流程是否中断 | `QUIT_ON_LVS_ERROR` | — |

**工程铁律：看报告，不看返回码。**

补充：`QUIT_ON_LVS_ERRORS`（复数）是**无效键**，真正的键是单数。

```bash
  designs/sram_test/runs/repro_lvs/logs/signoff/40-*.lvs.log | head

  designs/sram_test/runs/repro_lvs/config.tcl   # 确认快照里是错误值
```

注意：`FP_PDN_MACRO_HOOKS` 只在 **floorplan 的 PDN 生成**阶段生效，必须 `-overwrite` 全新跑，增量跑不生效。

## 8. 面试口径

**30 秒版**

> 我做过一个带 SRAM 宏的设计，LVS 报 37 个错。我先看四类分解：网数差 2、器件差 0、未匹配网 4、器件 18、引脚 13，加起来正好 37——说明不是一个 bug 而是连锁。器件差 0 排除库问题；网数差 2 说明有一电一地成了独立网。日志里 `u_sram/vccd1 | _NC30` 证实宏电源脚悬空。根因是 `FP_PDN_MACRO_HOOKS` 参数顺序写反：第 4、5 位该填引脚名，我填成了网名，OpenROAD 匹配不到 iterm 但不报错。改一行后归零。我做了三态对照，改回去又能复现 37。

**会被追问的三点**

1. **为什么工具不报错？** —— `add_global_connection` 的 pin pattern 匹配不到 iterm 时静默跳过，这是它的设计（一个 pin pattern 可能匹配 0 个或多个实例）。
2. **怎么避免？** —— 跑完 floorplan 后检查 PDN 报告里宏电源脚是否连上；或在 signoff 前 grep LVS log 的 `Net: .* \| Net: _NC`；或对宏数量做断言。
3. **为什么不是器件库问题？** —— `device count difference = 0`，两侧器件数完全一致，只是网连错了。

## 9. 这道题真正学到的东西

| 层次 | 内容 |
|---|---|
| 现象层 | 37 = 2+4+18+13 四类求和，先做自洽校验 |
| 判据层 | `device count difference = 0` 一句话排除整个器件库方向 |
| 取证层 | 从 log 里找 `Net: A \| Net: _NC`，而不是凭印象 |
| 根因层 | 参数顺序 + 工具静默失败 = 最难查的一类 bug |
| 方法层 | 单变量回退 + 三态对照（0→37→0），比拼记忆可靠 |
| 纪律层 | `[SUCCESS]` 只代表流程走完，报告才是结论 |
