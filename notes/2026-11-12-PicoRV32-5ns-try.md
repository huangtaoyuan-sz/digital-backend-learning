## 🔍 V1：5 ns 到底差在哪（路径拆解）
最差路径：`_16589_` → `mem_la_addr[31]`（reg2out）
```
arrival  4.26 ns
required 3.75 ns  (= 5.00 - 0.25 uncertainty - 1.00 IO)
slack   -0.51 ns
```
### 延时构成
| 段 | 数值 | 占 arrival |
|---|---|---|
| **① 时钟插入** | **1.53 ns** | **35.9%** |
| ② clk→Q | 0.42 ns | 9.9% |
| **③ 串行 buffer 链（5 级）** | **1.19 ns** | **27.9%** |
| ④ 逻辑门（a311o + o31a） | 0.84 ns | 19.7% |
| ⑤ 输出缓冲 | 0.22 ns | 5.2% |
| ⑥ 互连 | 0.08 ns | 1.9% |
### 预算账（关键）
```
周期 5.00
- uncertainty  0.25
- IO 预算      1.00
──────────────
required       3.75
固定开销
- 时钟插入     1.53   ← 占周期 30.6%
- clk→Q        0.42
──────────────
逻辑预算       1.80 ns
实际逻辑       2.31 ns
超支           0.51 ns  ← 正好是 WNS
```
**结论：5 ns 下 64% 的周期被固定开销和接口吃掉（1.53 + 0.42 + 0.25 + 1.00 = 3.20）。**
### 三个根因
| # | 根因 | 证据 | 可修性 |
|---|---|---|---|
| 1 | **5 级串行 buffer 链**占 1.19 ns | 和 8 ns 时同一个病（当时 4 级） | 改约束让 resizer 重做 |
| 2 | `o31a_4` 单级 0.54 ns，slew 0.19→0.53 | 驱动不足/负载大，家族最大只能 `_4` | 只能减负载 |
| 3 | 时钟插入 1.53 ns（占 30.6%） | 4 级 CTS | 减 CTS 级数 |

## 💥 V1 为什么没跑完：内存
### 现象
```
[INFO]: Running Placement Resizer Design Optimizations...
（此后无输出，11 分钟零写入）
errors.log 不存在  ← 不是报错，是被杀
```
### 根因链
```
WSL 没设内存上限（默认最多吃主机 50%）
→ 5 ns 下 resizer 内存峰值暴涨
→ 主机内存 96%
→ Linux OOM killer 杀掉 openroad
```
### 中间踩的两个坑
**坑 1：`docker ps` 显示两个容器同时在跑**
以为第一次死了，又启动了第二次 → 两个 flow 同时吃内存 → 7.6 GB 瞬间见底。
**教训：判断"死没死"不能看终端，要看 `docker ps`。**
```bash
# 容器有自己的 PID 命名空间，宿主 ps 看不到 openroad
docker ps          # 有输出 = 还在跑
docker stats --no-stream   # 每个容器吃多少内存
```
**坑 2：低内存配置漏了关键开关**
我只关了 `PL_RESIZER_TIMING_OPTIMIZATIONS` 和 `GLB_RESIZER_TIMING_OPTIMIZATIONS`，
**漏了真正吃内存的 `PL_RESIZER_DESIGN_OPTIMIZATIONS`（placement 的 9-resizer）。**
正确做法：OpenLane 的 resizer 有 **四个** 独立开关，要关就四个一起关。
```json
"PL_RESIZER_DESIGN_OPTIMIZATIONS": 0,
"PL_RESIZER_TIMING_OPTIMIZATIONS": 0,
"GLB_RESIZER_DESIGN_OPTIMIZATIONS": 0,
"GLB_RESIZER_TIMING_OPTIMIZATIONS": 0
```
### 内存限制配置
```ini
# C:\Users\hty13\.wslconfig
[wsl2]
networkingMode=mirrored
memory=8GB
swap=4GB
processors=6
```
改完 `wsl --shutdown` 重启，`free -h` 显示 Total 7.6 GiB（之前 15 GiB）。

## 📉 V2：关掉优化后发生了什么
**流程跑完了**（DRC 0 / LVS 0 / GDS 生成），但：
| 指标 | V1（有优化） | V2（无优化） | 变化 |
|---|---|---|---|
| setup WNS | -0.51 | **-5.57** | **恶化 5.06 ns** |
| 面积 | 0.2486 | **0.2245** | **减小 10%** |
| 布线长度 | 672,122 | 620,478 | 减小 8% |
### 结论 ①：resizer 在 5 ns 下贡献了约 5 ns 的优化量
```
有 resizer：-0.51
无 resizer：-5.57
差值       5.06 ns
```
**5 ns 约束下的时序收敛几乎完全依赖 resizer 的 upsizing / buffer 插入。**
### 结论 ②：面积-时序 trade-off 的极端案例
```
面积 -10%  ←→  时序 -5 ns
```
**反直觉但合理**：resizer 为修时序会升驱动，面积变大。关掉后 cell 变小、面积降，代价是延时暴涨。
### 结论 ③：hold 违例固定在 `resetn` 路径
```
Startpoint: resetn (input port)
Endpoint:   _16951_ (flip-flop)
slack -0.14
```
**根因**：5 ns 下 `IO_PCT = 0.2` → `input_delay = 1.0 ns`（8 ns 时是 1.6）。
复位路径余量不足，且 resizer 被关掉，没人修 hold。

## 📌 三个"非时序"连带效应
### ① IR drop 超标（3.12% → 5.15%）
**不是 PDN 变差，是功耗涨了**：
```
8 ns：63.4 mW
5 ns：104 mW   ← 频率 1.64 倍，动态功耗同比上涨
```
PDN 没变，电流翻倍 → 压降从 3.12% 涨到 5.15%。
### ② 天线恶化（33/27 → 57/35）
5 ns 下 cell 更多 upsizing、布局更密 → 长线更多 → 天线比恶化。
### ③ 报告文件名编号变了！
**因为禁用 4 个 resizer pass，流程步骤编号整体前移：**
| 8 ns 版 | 5 ns 低内存版 |
|---|---|
| `31-rcx_sta.summary.rpt` | **`25-rcx_sta.summary.rpt`** |
| `39-*.lvs.rpt` | **`33-*.lvs.rpt`** |
| `41-antenna` | **`35-antenna`** |
**教训：分析报告时先 `ls` 看实际文件名，不要硬编码编号。**

## 💡 学到了什么
1. **提频实验的第一步是算预算，不是改配置**
   `5.0 - 0.25 - 1.0 - 1.53 - 0.42 = 1.80 ns` 留给逻辑，而逻辑实际要 2.31 → 必然违例。
2. **"能不能跑完"取决于内存，不取决于设计**
   同一份设计，8 ns 跑得动，5 ns 的 resizer 就把 7.6 GB 吃掉。
3. **判断进程死活要看容器，不看终端**
   `docker ps` / `docker stats` 才是真相。
4. **降级配置要关全**
   OpenLane 的 resizer 有四个开关，漏一个就等于没关。
5. **"跑完了"≠"结果有用"**
   V2 跑完了，但 WNS -5.57 只是因为关掉了优化，不能用来判断"设计能不能跑 5 ns"。
6. **报告编号会随流程步骤变化**
   禁用某些 pass 后，`31-` 会变成 `25-`。
